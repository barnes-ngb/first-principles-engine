# UX AUDIT BOOKS 2026-09 — the whole book area, walked as one thing

**Run date:** 2026-09-03 · **Baseline:** `origin/main` @ `8b9d1d08` (FEAT-178 merged) · **Branch:** `claude/ux-audit-books-2026-09-56rif7` · **Ledger:** FEAT-179 (the audit) + one `UX-` row per open P1 · **Ids:** UX-102 → UX-147 (UX-101 was the last filed; UX-92 / UX-93 are re-verified below under their existing ids)

**Why this audit exists.** Owner direction (Nathan, 2026-09-03): *"might be worth reviewing everything in the book area currently to smooth it out and ensure it makes sense."* Books is the area that has changed most in the last ten days — FEAT-169/172/173 (the sight-word channel, the failure messages, the active profile as context), 174 (the style picker wins), 175 (the weekly art budget), 176 (readable-at-level + the honest line), 177 (show the whole picture), 178 (help sheets and hints), plus the Stickers work (160 / 165–168). Every one of those runs was reviewed for data safety and honesty; **no run has owned whether the area reads as one thing.** The August audit (`UX_AUDIT_2026-08.md`, FEAT-153) walked Stickers (§12) and nothing else under Books. This document is the model applied to the rest: **walk, file, rank — fix nothing**, with the one sanctioned exception (pure label-text corrections where the current word is dishonest about the data model; every applied fix is in §0 and the PR body).

**Method.** The app cannot be run from this environment; the audit walks what the JSX says the screen shows, route by route in the order the run prompt set (shelf → Generate a Book → Create Sight Word Book → Book Editor → Reader → Review chat → Stickers → Sight Words dashboard → Print). Every string a parent or kid sees is quoted verbatim with `file:line`. Where a claim needs a runtime, it says **unverified**. Kid surfaces (reader, review chat, the kid shelf) got a read-only pass — flag, never touch. Each surface was asked the August audit's five questions plus three for Books:

1. **Label honesty** — does every control say what it does in the data model's own truth?
2. **First-glance hierarchy** — what does each screen lead with, and is that what the parent (or kid) came for?
3. **Consistency** — same concept, same word, everywhere (the naming table in §4.1 is the deliverable).
4. **Dead ends and forced detours** — no way back; a screen visit for a one-tap act.
5. **Absurd states** — computed copy that can say something ridiculous.
6. **The journey** — can Shelly go idea → readable story → illustrated → printed without a surprise, and does a paid step ever arrive without warning (FEAT-178 claimed every door; §10 verifies).
7. **The kid path** — can London (6) open and read a book made for him with no parent at the phone, and where does the UI itself make him read a word above his level?
8. **Honesty of the new lines** — do FEAT-169's failure messages, FEAT-172's word-source line and FEAT-176's honest line compose on one draft turn without contradicting each other or running to three sentences a parent won't read?

**Severity.** **P1** = confusing-or-dishonest (a control or copy that misleads about what happened / what a tap does, a paid step with no warning, or a state that strands a family member). **P2** = inconsistent (same concept, different words or behaviour) or a real paper cut. **P3** = polish. P1s get individual ledger rows; this doc carries everything.

**Tally.** 46 findings filed (UX-102 → UX-147): **10 P1** (9 open, 1 fixed in-run) · **31 P2** · **5 P3** (several as bundles). Plus UX-92 and UX-93, the two oldest open P1s in the area, re-verified against this baseline and still standing.

## 0. The one exception: fixes applied in this run

Per the rails, only **pure label-text corrections where the current word is dishonest about the data model** were applied. One family qualified:

- **UX-103 (applied).** The shelf's creator labels named a person the data model does not. `Book.createdBy` is `'parent' | childId`, and the type's own comment says `'parent' = Mom/Dad` (`src/core/types/books.ts:275`); the Book Editor's matching select already reads **"Me (Mom/Dad)"** (`BookEditorPage.tsx:1081`). Yet the shelf's per-card chip said **"By Mom"** (`BookshelfPage.tsx:572`) and the creator filter chip **"Mom's Books (n)"** (`:395`) — so a book Nathan makes, or any legacy book (absent `createdBy` → treated as `'parent'`), is stamped as Mom's. Changed: chip → `By a parent`, filter → `Parents' books (n)`. Text-only; the two strings appear in no test. The same "a parent" wording the August audit settled for the Watch Library (UX-02) — one phrase for the `'parent'` value everywhere.

Candidates examined and **not** fixed here because the dishonesty is in behaviour, not the word: "Publish" on Create Sight Word Book (UX-121 — it writes `status: 'complete'`; the fix is to pick one word with the editor's "Finish", a consistency call for Nathan), "Your book is ready!" (UX-115 — the string is right when true; the bug is that it renders when it is false), "Print" / "Download PDF" (UX-145 — five labels for one `pdf.save()`; a rename is a naming decision, not a correction), and every kid-surface label, which stays filed per the read-only rail.

## 1. Entry points — the shelf (`BookshelfPage.tsx`, `/books`)

**What the shelf leads with.** Title "My Books" (`:306`), then — before the first book — up to five rows of controls on a parent phone: the type toggles `All / My Stories / Generated / Sight Words` (`:324-335`); the button row `Stickers · Create Sight Word Story · Sight Word Progress · Grandparent guide` (`:339-378`); `Made by: All / Mom's Books / Kids` (`:385-407`); the child chips + `Together` (`:412-436`); the theme chips (`:439-478`); the sticker-tag chips (`:481-504`). The grid then opens with a dashed **"New book"** tile (`:541-565`) and the cards. Cards sort drafts first (`:275-279`) — the one hierarchy decision that is right: a draft in progress is what she came back for.

- **UX-102 · P1 — three ways to make a book, and nothing says which door is for what.** "New book" opens a dialog titled "Make a New Book" with two tabs, **"Blank Book"** and **"Generate a Book"** (`:986-987`, defaulting to Generate); inside the Generate tab a `text.secondary`, `p: 0` link reads **"Use Story Guide (guided questions)"** (`:1050`); and the header carries a fourth door, **"Create Sight Word Story"** (`:357`), plus the evaluation banner's **"Create Targeted Story"** (`EvaluationBookBanner.tsx:70`), which lands on the same page. Four generators, five verbs (Make / Generate / Create / Use), zero explanatory copy. The question the run prompt asks — *would Shelly know which door to use for "a book for London with his words"?* — has two correct answers today (the chat takes typed words since FEAT-172 **and** falls back to his practice list; Create Sight Word Story takes a typed list) and one wrong-looking one (Story Guide always folds in his weak words, §2). She cannot tell from the shelf. *Fix (structure, Batch C):* one "Make a book" door with three labelled choices and a one-line "when to use it" under each; retire the Story Guide link from inside the chat tab (it is a competing generator, not a sub-mode of this one); fold Create Sight Word Story's typed-list case into the chat's already-working typed-list path or say plainly what it does differently (§3, UX-118).
- **UX-103 · P1 · FIXED (this run)** — "By Mom" / "Mom's Books" over `createdBy: 'parent'`. See §0.
- **UX-104 · P2 · FIXED (FEAT-181, PR #1743) — the type filter mixes three axes and the "AI" chip misses half the AI books.** The toggles are `My Stories` (= `bookType` neither `sight-word` nor `generated`, `:328`), `Generated` (`bookType === 'generated'`, `:331`) and `Sight Words` (`bookType === 'sight-word'`, `:334`). On a **parent** shelf "My Stories" is every hand-made book by anyone, so "My" is false; "Generated" is a *how*, "Sight Words" is a *what*, and a Create-Sight-Word-Story book is **both** AI-generated (`source: 'ai-generated'`, `CreateSightWordBook.tsx:134`) and a sight-word book, yet it is excluded from "Generated" and gets no **"AI"** chip (`:750` gates on `bookType === 'generated'` only). *Fix (wording, Batch A):* `All / Made by hand / Written by AI / Sight-word books`, and key the AI chip on `source === 'ai-generated'`.
- **UX-105 · P2 — the parent shelf leads with controls, not books.** Five control rows precede the grid (above). Three of the header buttons are not about *this* shelf at all (Stickers is its own page; Sight Word Progress is a dashboard; Grandparent guide opens a print window). *Fix (structure):* books first with the type toggle; move Stickers / Sight Word Progress / Grandparent guide into a "More" row or the nav; collapse the filters behind a single "Filter" chip when more than one is showing.
- **UX-106 · P2 · FIXED (FEAT-181, PR #1743) — "Continue reading →" opens the review chat, not the reader.** A card whose Per-Page Review is partway (`isReviewInProgress`, `:576-580`) shows **"Continue reading →"** (`:791`) and taps through to `/books/{id}/review` (`:591`) — the "How does this page sound?" approve / change surface (§6), which the kid experiences as being read *to*, and which a parent will read as "the reader". The finished-review chip is fine; this one names the wrong act. *Fix (wording):* `Finish "Read it to me" →` — the editor already calls the surface **"Read it to me 🎧"** (`BookEditorPage.tsx:1163`); use its name.
- **UX-107 · P3 · PARTLY FIXED (FEAT-181, PR #1743 — (e) only) — bundle.** (a) The per-child chip counts `b.childId === child.id` (`:423`) while the filter it drives also includes `contributorIds` (`:264`), so a Together book is filtered in but not counted. (b) Filtering to nothing shows only the "New book" tile — the `EmptyState` (`:506`) fires on `books.length === 0`, never on `sortedBooks.length === 0`, so a parent who picked `Sight Words` + `Kids` sees a lone dashed tile with no "no books match" line. (c) The `Together` filter exists on the shelf (`:429-434`) but the only way to *make* a Together book is the switch inside the editor (`BookEditorPage.tsx:1197-1216`); `createBook` is always called with `isTogetherBook` `undefined` (`:147-153`). (d) Lincoln's card titles render at `0.55rem` in the pixel font (`:690`) — a title of any length is unreadable at that size on a phone (cosmetic-by-name is allowed; the size is the finding). (e) The kid shelf shows the same toggle labels as the parent's: **"Generated"** is not a word London reads (§7 note).
- **UX-108 · P1 — the owed decision: a resumed draft under a different active child is written for the wrong child.** Since FEAT-173 the active profile is the context, and a **parent** shelf lists every child's drafts (`useBookshelf(…, isParent)` loads all, `useBook.ts:786-796`). Tapping a dashed "Continue making this story →" card (`:587`) reopens the chat, which reads **the active child's** practice words (`useBookGenerateChat.ts:232-239`), sends **the active child's** `childId` to `generateStory` (`:711-731` — the server sizes the level from it) and names the active child in every line — while `persistStory` spreads `...current` (`:360-382`) so the doc's `childId` / `createdFor` stay the *original* child's. So: Shelly on Lincoln's profile taps London's half-made story → a story sized to Lincoln's level with Lincoln's words is written into London's book, on London's shelf. Nothing on the card says whose draft it is (it shows "By a parent", not "for London"), and nothing in the dialog does either. **Recommended behaviour:** (1) the card carries the child — `for London` — next to the creator chip (`createdFor` is already stored); (2) on resume, if `book.childId !== activeChild.id`, the chat renders one line instead of the composer — *"This draft is London's. Switch to London in the header to keep making it."* — and does not read, send or write anything. That keeps FEAT-173's rule (no second child picker, the header is the context) and makes the mismatch impossible rather than silent. Filed with a ledger row.

## 2. Generate a Book (`StoryGuidePage.tsx` → `BookGenerateChat.tsx` → `useBookGenerateChat.ts`; `StoryLengthSelector.tsx`, `GenerationProgress.tsx`, `useBookGenerator.ts`, `useBookIllustrator.ts`)

**The sequence, read end to end as a parent.** Empty thread: *"Let's make a story! What's it about?"* (`BookGenerateChat.tsx:330`). Type an idea → the echo turn *"Here's what I heard: "…". Want me to start the story?"* (`useBookGenerateChat.ts:198`) → under it, when a list is in play, *"I'll try to work in the words you asked for: …"* or *"I'll try to weave in some of London's practice words: …"* (`storyPracticeWords.ts:267 / :262`) → **"✓ Yes, start my story!"** (`:406`). A second message before the tap gets *"Should I ADD that to your story, or CHANGE the idea to that?"* with **"+ Add it" / "↺ Change it"** (`:417 / :425`) and the composer's helper *"Tap Add or Change above to continue."* (`:573`). The draft turn: *"Here's your story! "Title" — it uses your practice words: a, b." + the FEAT-176 clause* (`storyPracticeWords.ts:367-387`), then the pages with a 🔊 per page, the revise composer, the length selector (hidden once a draft exists, `:601`), the **"Illustration style"** strip with its "?" (`:613-617`), **"✓ I like the whole story!"** (`:651`) with the FEAT-178 hint under it (`:656-662`), and **"Cancel — start over"** only before a draft (`:663-672`). Commit → *"Illustrating page 3 of 10… Hang tight — this can take up to a minute."* (`:534-538`) → hand-off to the editor (parent) or the review chat (kid) (`BookshelfPage.tsx:1060`); at the cap, *"Your story is saved! {ART_QUOTA_MESSAGE} You can add photos or drawings in the editor."* and **"Okay — take me to my book"** (`:499-509`), which waits for the tap. Read cold, the spine of it makes sense the first time. The findings are at the joins.

- **UX-109 · P1 — the FEAT-176 honest line is read aloud to the child.** On the first story draft the chat queues TTS of `lastAi.content` followed by every page (`BookGenerateChat.tsx:204-216`). Since FEAT-176 that content ends with *"3 words may be above London's level: castle, dragon, kingdom. (estimated from age — set London's phonics level under Working Levels on the Skill Snapshot for a better fit)"* (`storyPracticeWords.ts:343-345`). The clause was written for the parent's eyes — blameless on the page, and deliberately so — but the speaker is the kid's, and a six-year-old sitting beside the phone hears his own name and "above London's level" before he hears the story. The charter says struggles are data, not something the child is told about himself by a robot voice. *Fix (small guard, Batch B):* speak the base line and the pages only — build the TTS queue from `storyDraftMessage(...)` **without** the readability clause (a second exported helper, or speak `Here's your story! "${title}"` directly). The clause stays on screen for the parent.
- **UX-110 · P2 — answering the question the chat just asked is treated as a new idea.** *"Want me to start the story?"* is a yes/no question, and the composer is live under it. A kid (or parent) who types **"yes"** gets *"Should I ADD that to your story, or CHANGE the idea to that?"* (`useBookGenerateChat.ts:637-656`), and "+ Add it" produces the idea *"a dragon who finds a cave and yes"* (`joinIdeas`, `:185-195`). *Fix:* treat a bare affirmative (`yes`, `yes!`, `ok`, `go`, `start`) as the Yes tap and a bare negative as a no-op with a nudge; or lock the composer while the Yes button is showing, the way it already locks while Add/Change is pending (`:150-153`).
- **UX-111 · P2 · FIXED (FEAT-181, PR #1743) — three voices in one draft turn, and a clause that names a path with no link (question 8).** Before the tap the line says *"…some of **London's** practice words"* (`storyPracticeWords.ts:262`); the draft turn says *"it uses **your** practice words: …"* (`:381`); the FEAT-176 clause then says *"above **London's** level"* (`:345`) — third person, second person, third person, in three consecutive lines of one conversation, on a surface where FEAT-173 decided the typist is the parent working in the child's profile. Worst case the turn reads: *Here's your story! "The Brave Knight" — it uses your practice words: the, and, said. 9 words may be above London's level: castle, knight, dragon, kingdom, bravely, sword and 3 more. (estimated from age — set London's phonics level under Working Levels on the Skill Snapshot for a better fit)* — four sentences, ~60 words, and a 20-word parenthetical telling a parent inside a book dialog to go to a Progress tab she cannot tap through to. The lines do **not** contradict each other (the word list is text-checked; the hard-word count is the server's untruncated total, `:333-337`), and nothing here runs to three *paragraphs* — but it is longer than a parent reads on a phone. *Fix (wording, Batch A):* one voice — third person with the child's name throughout ("it uses London's practice words"); drop the parenthetical to *"(level estimated from age)"* and move the "set the phonics level" advice into the "?" sheet, which is where FEAT-178 put every other explanation.
- **UX-112 · P2 — FEAT-169's named failures landed on one path; the sibling paths still say "trouble".** The revise loop sets the pre-169 string **"I had trouble with that. Try again?"** for both a no-reply and an unreadable reply (`useBookGenerateChat.ts:572, :577`) with no "nothing was lost" and no next step; the Story Guide says **"Failed to generate the book. Please try again."** (`StoryGuidePage.tsx:94`) over `useBookGenerator`'s **"Failed to generate story" / "Failed to parse story — please try again" / "Failed to save book"** (`useBookGenerator.ts:171, :186, :247`); the review chat says **"I had trouble changing that page. Try again?"** (`useBookReview.ts:322, :409`). Same call, same three failure shapes, one honest set of messages and three vague ones. *Fix (small guards, Batch B):* route all of them through `classifyStoryGenerationFailure` / `storyGenerationFailureMessage` with the button name swapped.
- **UX-113 · P2 — once a draft exists there is no way out but the shelf's Delete.** "Cancel — start over" renders only while `currentStory === null` (`BookGenerateChat.tsx:271, :663`), and `abandonDraft` is a documented no-op after a draft (`useBookGenerateChat.ts:892-902`). Closing the dialog (backdrop or the Blank tab's Cancel) leaves a dashed "Continue making this story →" card with no line saying so. A parent who decided the story is wrong has to close, find the card, open its ⋮ menu and Delete. *Fix (structure):* a "Discard this story" text button after the draft, confirm-gated, that deletes the draft doc; and one line on close — *"Your draft is saved on the shelf."*
- **UX-114 · P2 — a resumed draft cannot be illustrated, and the hint is the only thing that says so.** Resume rebuilds `sceneDescription` from `p.images?.[0]?.prompt ?? ''` (`useBookGenerateChat.ts:310`). A draft that was never illustrated has no images, so every page comes back scene-less; commit spends nothing and produces a text-only book; the FEAT-178 hint under the commit button honestly reads **"No pictures to make here · nothing to pay for"** (`artHelpContent.ts:641`) — correct, and baffling, because nothing says *why*. The data behind it: `storyToPages` drops the model's `sceneDescription` on save (`:156-168`) and only the illustrator writes it back as `prompt`. *Fix:* persist `sceneDescription` on the draft page (additive field) so a resumed draft illustrates like a fresh one; until then, a line under the hint — *"This draft's scene notes weren't kept — revise any page to get them back."*
- **UX-115 · P1 — the Story Guide's finish screen says "Your book is ready!" whatever happened.** `useBookGenerator` ends with a `phase: 'done'` progress whose `message` is the truth — *"Your story is saved! {ART_QUOTA_MESSAGE} …"* when the budget refused the pictures, *"Book created! N pages need illustrations — …"* when some failed, *"Your book is ready!"* only when all landed (`useBookGenerator.ts:284-295`). `GenerationProgress` hides `message` whenever `phase === 'done'` (`GenerationProgress.tsx:78`) and prints a **hard-coded** *"Your book is ready!"* (`:110-117`) — then `StoryGuidePage` navigates to the editor after 1.5 s (`StoryGuidePage.tsx:89-92`). A kid at the cap sees a green check and "ready", lands in an unillustrated book, and is never told why; the FEAT-168 refusal copy written for exactly this moment never renders on this path. *Fix (small guard, Batch B):* render `message` in the done state and drop the literal. Filed with a ledger row.
- **UX-116 · P2 — the Story Guide is a third generator with its own rules, reachable only from a buried link.** Compared with the chat it sits beside: no illustration style picker — `genStyle = isLincoln ? 'minecraft' : 'storybook'` (`StoryGuidePage.tsx:52`), so London cannot pick Comic Book here though FEAT-174 made the picker real; it **always** folds the child's weak words in (`getWeakWords().slice(0, 10)`, `:76`, shown as *"Sight words to practice"* `:252`, no opt-out) and because it passes them as `words` the book gets `sightWords` set (`useBookGenerator.ts:231`) — so a Story Guide book opens in sight-word-mode in the reader while a chat book does not (UX-123); its back button says **"Bookshelf"** (`:145`) where every other surface says "Back to My Books" / "Books"; its **"Generate My Book! →"** (`:289`) is a paid door with no hint and no "?" (UX-147); and its questions are name-keyed (`useStoryGuide(isLincoln)`, `:57`). *Fix (structure, with UX-102):* either give it the chat's style strip, length + hint, and the same word-source line, or retire it — the chat now covers "tell me your idea" and Create Sight Word Story covers "here are the words".

**Verified clean (asked, and the answer was good):** the Yes button is withheld while the practice list is loading and says why (`:371-381`); the pre-tap word line names its source (typed vs practice) and never dresses one as the other; the draft turn checks the words against the page text, not the model's claim (`practiceWordsUsedIn`); the failure messages keep the idea and say "Nothing was lost"; the cap notice holds the hand-off until a tap so a kid actually reads it; the commit hint counts scene-bearing pages, not the length, so it never overstates the spend.

## 3. Create Sight Word Book (`CreateSightWordBook.tsx`, `useStoryGenerator.ts`, `/books/create-story`)

**The screen.** "Back to My Books" (`:207`) · title **"Create a Sight Word Story"** (`:212`) · a words box *"Sight words (type or paste, comma-separated)"* with *"Word count: N"* (`:225-234`) · *"Or pick a list:"* chips `Dolch Pre-Primer · Dolch Primer · London's Starter Words · Words needing work · Try sample story` (`:245-279`) · a **"Theme"** text field, placeholder *"Minecraft adventure with a cat"* (`:285`) · *"Pages: N"* slider 5–15 (`:295-305`) · **"Generate Story"** (`:317`) · then *"Preview: Title"*, a *"Missed words: …"* warning (`:331`), the pages with chips, and **"Edit in Book Editor"** / **"Publish"** (`:370 / :379`).

- **UX-117 · P1 — a failed generation shows nothing, and the honest line never reaches this surface.** `useStoryGenerator.generateStory` does `JSON.parse(cleaned)` outside any `try` (`useStoryGenerator.ts:41-42`), and `handleGenerate` has no `catch` (`:91-101`). A reply cut short by the output budget — the exact failure Shelly hit twice in the chat before FEAT-169 — throws an unhandled rejection: `generating` clears (it is `useAI`'s flag), the button un-spins, `genError` stays `null`, and the screen is unchanged. The chat names that failure in three shapes; this door, which sends the *same* `generateStory` task (server reads `storyConfig.words ?? storyConfig.sightWords`, `functions/src/ai/tasks/generateStory.ts:386`), says nothing. And the server **does** run the FEAT-176 measurement here too and returns `readability` — this hook discards it (`GeneratedStory` has no such field), so a story the server measured as above London's level is previewed with no honest line at all. *Fix (Batch B):* wrap the parse, classify with `classifyStoryGenerationFailure`, render the house-shape message; read `result.readability` and show `storyReadabilityClause` above the preview. Filed with a ledger row.
- **UX-118 · P2 — it duplicates the chat and nothing says when to use which.** Both call `generateStory`; both take a typed word list (FEAT-172 gave the chat one); both let a parent pick a length; both land in the editor or the reader. The differences are real but undocumented: this one takes preset lists (Dolch, "Words needing work"), writes `book.sightWords` so the reader runs in sight-word mode (UX-123), has no illustration step at all (the book is text-only until the editor), reports the model's own `missedWords` (UX-119), and lets a parent set pages 5–15 (UX-120). Its title says **Story**, the shelf button says **Story**, the banner says **Targeted Story**, the dialog says **Book**, the Story Guide says **Book** — one product, two nouns. *Fix (structure, with UX-102):* one door map; and pick one noun — the thing on the shelf is a **book**.
- **UX-119 · P2 — "Missed words:" repeats the model's claim.** `preview.missedWords` (`:329-333`) is whatever the server's parse said; the chat, after FEAT-169, computes which words actually appear in the page text (`practiceWordsUsedIn`) precisely because the model's list was not to be trusted. Same task, two standards. *Fix:* compute missed = requested − `practiceWordsUsedIn(pages, requested)` on the client.
- **UX-120 · P2 — a 5–15 page slider beside a 6 / 10 / 14 chooser.** The chat and Story Guide offer *Short 6 · Normal 10 · Long 14* (`storyPageTargets.ts`, the priced product sizes); this slider offers 5–15 in steps of 1 (`:300-302`). The server's budget scales per page and clamps only tokens (`storyPageBudget.ts:71`), so 15 is a real request — a page count no other door offers and no help sheet mentions. *Fix:* use `StoryLengthSelector` here too.
- **UX-121 · P2 · FIXED (FEAT-181, PR #1743) — "Publish" means "save as finished".** The button (`:379`, *"Publishing..."*) writes `status: 'complete'` (`:129`) and opens the reader; the shelf then shows **"Finished"** (`BookshelfPage.tsx:765`) and the editor's chip is **"Finish"** (`BookEditorPage.tsx:1186`). "Publish" is the monthly-review verb (parent → kids) and implies a gate this write does not have. Not fixed in-run because the honest word is a consistency decision (Finish vs Publish) rather than a correction. *Fix (wording):* `Finish book` / `Finishing…`.
- **UX-122 · P3 · PARTLY FIXED (FEAT-181, PR #1743 — (a) wording + (d)) — bundle.** (a) The prefill banner renders only for `source === 'word-wall'` (`:216`), so the evaluation banner's hand-off (`source: 'evaluation'`) prefills the words silently with no banner; and the banner's copy, *"They're struggling with these patterns."*, is deficit wording on a page whose sibling surfaces say "practicing". (b) **"Try sample story"** (`:274-279`) loads `SAMPLE_STORY` and sets a Minecraft theme on a production parent surface; "Publish" then writes the sample as a real finished book on the child's shelf. (c) **"London's Starter Words"** is gated on `!isLincoln` (`:256`) and `CHILD_BOOK_DEFAULTS` / `difficulty` are keyed by name (`:55-56`, `sightWordMastery.ts:106-121`) — content by name, allowed as cosmetic, but it means a third child gets London's defaults with London's label. (d) The **"Theme"** field (`:285`) is actually the story idea (it becomes `storyIdea` server-side, `generateStory.ts:387`); "theme" elsewhere means the shelf's world tag (§4.1). ## 11. Cross-cutting patterns (why this keeps happening)

1. **Three generators grew up separately and nobody drew the map.** The chat got FEAT-169 → 176 (named failures, text-checked word lines, the honest line); Create Sight Word Story and the Story Guide got none of it and still speak the older, vaguer copy (UX-112, UX-117, UX-119). A fix that lands on "the story generator" lands on one of three.
2. **The new honest line was written for the eye and delivered by the ear.** FEAT-176's clause is careful on the page and wrong out loud (UX-109). Any string that a kid-surface TTS will read needs the question *who hears this?* asked at review.
3. **Success states are hard-coded while the outcome is computed.** *"Your book is ready!"* (UX-115), *"Great job!"* (UX-135), *"Saved to your gallery automatically"* beside a Save button (UX-128). The August audit's pattern #3 with the polarity flipped: not absurd zeros, but celebrations that ignore the value that was computed one line above them.
4. **Controls that promise ownership and change theming.** "For" (UX-124), "By" shown to kids (UX-127), the cover's "By {active child}" (UX-133): the book's own `createdBy` / `createdFor` / `childId` are three fields the UI reads inconsistently.
5. **Name-keyed lists produce two vocabularies for one thing.** `AI_SCENE_STYLES_LINCOLN` vs `_LONDON` (UX-126), `'lincoln' | 'london'` chips (UX-141), Story Guide questions and style by name (UX-116). Cosmetic-by-name is allowed; a *different set of labels* per child for the same recipes is not cosmetic — it is a consistency bug with a name on it.
6. **The confirmation budget, again.** "Delete page" unconfirmed and un-undoable (UX-130); one "Remove background" confirmed, the other not (UX-129); "Discard" on an already-saved reimagine (UX-128). One rule would settle all three: *destructive and not undoable → confirm; undoable → don't.*
7. **Same noun, five words.** §4.1. Most of it is a Batch A string pass; the reason it accreted is that each run named its own thing ("scene", "background", "illustration", "picture", "image") and no run was asked to reconcile.
